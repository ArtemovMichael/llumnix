## Проверяемый вопрос

При какой нагрузке Llumnix сокращает ожидание и нарушения SLO и при какой
цене миграции этот выигрыш пропадает?

## Сравниваемые варианты и baseline

Сравним три варианта:

- Round-Robin: то есть запросы распределяются по кругу, без переносов
- Least-loaded: выбирается наименее загруженный по памяти экземпляр с учётом очереди, без переносов.
- Llumnix: используется виртуальная нагрузка и перенос выполняющихся запросов.

Во всех запусках используем одну и ту же последовательность запросов.
Параметры экземпляров, данные о времени обработки и порядок локальной очереди
тоже одинаковые. Дополнительно запустим
Llumnix с тем же правилом назначения, но без миграций, чтобы оценить пользу переносов.

Для Least-loaded используем собственное правило оценки памяти и очереди.
В статье сравнение включает INFaaS++ и Llumnix-base с миграциями и отключёнными
приоритетами ([§6.1](https://www.usenix.org/system/files/osdi24-sun-biao.pdf#page=11)).

## Данные или нагрузки

Для каждого запроса задаём ID, время поступления в секундах, длины входа
и ответа в токенах и приоритет. Длина ответа известна только движку.

Основная нагрузка — синтетические трассы по методике
[статьи Llumnix, §6.1](https://www.usenix.org/system/files/osdi24-sun-biao.pdf#page=10):

- Поступления — пуассоновский поток с интенсивностью $\lambda$ запросов/с.
  Для всплесков используем гамма-распределение интервалов с CV = 2 и средним
  $1 / \lambda$: форма $1 / CV^2$, масштаб $CV^2 / \lambda$.
  CV = 1 соответствует экспоненциальным интервалам.
- Вход и ответ независимо имеют длину 1024 токена с вероятностью $p$,
  иначе — 128. Базовое $p = 20\%$. Это наше упрощённое распределение.
- Базовый приоритет — normal. В отдельной серии случайно назначаем
  10% запросов класс high без учёта длины. Доля high взята из §6.4 статьи.

Дополнительно используем [BurstGPT](https://github.com/HPMLL/BurstGPT):
пары длин и реальные времена поступлений. Интенсивность меняем масштабированием
интервалов, сохраняя длины и порядок; первое поступление принимаем за ноль.
В статье из BurstGPT берутся длины при синтетических поступлениях (§6.1).

Зафиксируем файл, версию и фильтры по модели и типу запроса. Оставим успешные
запросы с положительными длинами, сохраним исключения и причины отбора.
Elapsed time содержит полное время обслуживания; профили prefill/decode
выберем отдельно.

## Конфигурации и план запусков

Используем два одинаковых экземпляра с фиксированной KV-памятью.

| Параметр | Значения |
| --- | --- |
| Интенсивность | 0,5 / 1 / 1,5 / 2 × $\lambda_{\mathrm{ref}}$ |
| Вероятность длинного входа и ответа $p$ | 0%, 20%, 50% для синтетики |
| Доля high | 0%, 10% |
| Коэффициент стоимости миграции | 0 / 0,5 / 1 / 2 / 4 |

В базовой серии: $\lambda_{\mathrm{ref}}$, $p = 20\%$, только normal,
коэффициент миграции 1. Меняем один параметр, остальные сохраняем.
Коэффициент умножает время копирования и остановки запроса; объём KV
и правила резервирования остаются прежними.

Для каждого источника нагрузки выберем $\lambda_{\mathrm{ref}}$ по пилоту
Least-loaded. Предлагаемый критерий — минимальная проверенная интенсивность,
при которой среднее ожидание достигает среднего времени изолированного
исполнения. При необходимости расширим сетку пилота. Сохраним результаты
и зафиксируем $\lambda_{\mathrm{ref}}$ для всех политик и серий этого источника.

### Повторы

| Этап | Запросов на трассу | Повторов | Seeds |
| --- | ---: | ---: | --- |
| Пилот | 1000 | 5 | 0–4 |
| Основной эксперимент | 10 000 | 10 | 100–109 |

Для синтетики повтору соответствует новый seed; 10 000 запросов — объём трассы
из §6.1 статьи. Для BurstGPT используем отдельные непересекающиеся фрагменты;
seed задаёт искусственные приоритеты. Фрагменты пилота и основной серии разные.

Трассы заранее сохраняем и используем для всех политик. Вместе с ними сохраняем
параметры генерации или отбора, границы фрагментов, seed и контрольную сумму.
При изменении одного параметра сохраняем остальные характеристики трассы.

Числа предварительные. После согласования с командой, выбора
[профилей времени](project.md#выбранный-технический-путь) и пилота уточним
интенсивности, ёмкость памяти, стоимость миграции и размер основной трассы.

## Метрики

Полный запуск заканчивается после завершения всех запросов. Прерванные запуски
отмечаем как неполные и анализируем отдельно.

| Метрика | Расчёт |
| --- | --- |
| Начальное ожидание, с | Первое начало prefill минус поступление |
| Нарушения SLO, % | $100 N_{\mathrm{late}} / N$; нарушение, если $t_i^{\mathrm{finish}} - t_i^{\mathrm{arrival}} > S_i$ |
| Память, блоки | Средняя по времени и пик суммы занятых и зарезервированных KV-блоков по экземплярам |
| Миграции, шт. | Успешные и отменённые переносы отдельно, каждый ID учитываем один раз |

$N$ — число запросов, $N_{\mathrm{late}}$ — число нарушений SLO.
Ожидание, полное время и SLO считаем по всем запросам и отдельно для normal/high.
Для пустого класса пишем «нет запросов». Для времени сохраняем среднее, P95 и P99;
квантиль $q$ — элемент $\lceil qN \rceil$ отсортированного ряда с нумерацией от 1.
Prefill latency в статье включает также обработку входа до первого токена
([§6.1](https://www.usenix.org/system/files/osdi24-sun-biao.pdf#page=11)).

Память измеряем от первого поступления до последнего завершения. Для среднего
умножаем «занято + резерв» на длительность каждого интервала, складываем
и делим на общее время.
Пик — максимальная одновременная сумма по экземплярам.
Виртуальный запас используется только при оценке нагрузки планировщика.

### Пороги SLO

На отдельной калибровочной выборке найдём P95 изолированного времени исполнения
без очередей и миграций — $\tau$. Предлагаем $S_{\mathrm{normal}} = 2\tau$
и $S_{\mathrm{high}} = 1{,}5\tau$.

Калибровку проведём отдельно для синтетики при $p = 20\%$ и для фрагмента BurstGPT
с теми же фильтрами. Калибровочные данные исключим из основной серии.
После проверки порогов для коротких и длинных запросов и уточнения на пилоте
зафиксируем SLO для всех политик и серий одного источника нагрузки.

### Журнал событий

Сохраняем модельное время, номер события, его тип, ID запроса, экземпляр,
приоритет и SLO. Записываем поступление, начало prefill, завершение и изменения
занятой и зарезервированной памяти. Для миграции нужны её ID, источник,
получатель, начало и исход.

Одновременные события обрабатываем по номеру. Смену владельца и изменения
памяти при завершении миграции записываем одним атомарным переходом.

### Учебный пример расчёта метрик

[Журнал, ручной расчёт и способ повторения](checkpoints/01.md#проверка-расчёта-метрик)

## Проверка корректности

Допущения модели описаны в [проекте](project.md#упрощения). Проверим:

- Уникальность ID, допустимость времён и длин, распределения и воспроизводимость
  синтетики по seed; для BurstGPT — сохранение пар длин и масштабирование интервалов.
- По одному поступлению и завершению на запрос, порядок времён и одного
  логического владельца у активного запроса.
- Неотрицательность занятой и зарезервированной памяти, соблюдение лимитов.
  При отмене миграции резерв освобождается; завершённый запрос остаётся завершённым.
- Отсутствие активных запросов, резервов и переносов в конце полного запуска.

Решения политик сверим с [ручными примерами](checkpoints/01.md#расчётная-проверка),
расчёт метрик — с учебным журналом. Затем воспроизведём проверочный сценарий
в симуляторе.

## Обработка и анализ

Для запуска сохраним конфигурацию, политику, трассу, версию профилей, журнал
и метрики: число поступивших и завершённых запросов, нарушения SLO, ожидание,
полное время, память и миграции. Для неполного запуска укажем причину остановки.

Политики сравним попарно на одинаковых трассах. По повторам покажем среднее
и стандартное отклонение метрик и разностей; для SLO разность выражаем
в процентных пунктах. На графиках покажем зависимость от интенсивности,
вероятности длинных входов/ответов и стоимости миграции. Память рассмотрим
вместе с длительностью запуска. Команды обработки добавим после реализации.
