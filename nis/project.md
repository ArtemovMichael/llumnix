# Описание проекта

## Назначенное задание

[Задание P24](https://distsys.ru/osukhoroslov/nis2/src/branch/main/project-tasks/p24-llumnix.md)
по [статье Llumnix, OSDI 2024](https://www.usenix.org/system/files/osdi24-sun-biao.pdf).
Хотим понять, когда перенос LLM-запросов уменьшает ожидание и нарушения SLO,
а когда затраты на передачу KV-кэша становятся слишком большими.

## Выбранный технический путь

Будем писать дискретно-событийный симулятор на CPU. В нём учтём несколько
экземпляров, их очереди, prefill/decode, рост KV-кэша и переносы запросов.
Для первой точки используем ручные расчёты. Позже сверим с ними работу симулятора.

Берём LLaMA-7B FP16 на A10. Если не получим замеры авторов, время prefill/decode
и параметры памяти возьмём из [собственного прогона](checkpoints/01.md#модель-и-источник-профилей).

Рассматриваем только текстовые запросы. Каждая копия модели соответствует
отдельному GPU со своей очередью и KV-памятью. Характеристики обеих копий одинаковые.

## План реализации симулятора

На вход подадим список запросов с временем поступления, настройки копий модели
и замеры времени исполнения. Сохраним журнал событий и посчитаем
метрики из [плана эксперимента](experiment-plan.md#метрики).

1. У запроса сохраним [входные параметры](experiment-plan.md#данные-или-нагрузки),
   стадию обработки, число обработанных токенов и занятые KV-блоки.
   Отдельно укажем, на какой копии модели он выполняется. Для каждой копии
   будем учитывать очередь, активный batch, занятую и зарезервированную память.
   Планировщику не передаём будущие поступления и длины ответов.

2. Будем обрабатывать события по времени: поступление запроса, завершение
   шага prefill/decode, проверку миграций и этапы переноса. При одинаковом
   времени используем номер события. Время в симуляторе переходит к следующему
   событию. У каждой копии модели свой момент завершения шага, поэтому они
   могут работать одновременно. Состав batch меняем между шагами.

3. Prefill будем выполнять порциями, decode будет добавлять по одному токену
   каждому запросу за шаг. Время шага возьмём из профилей
   по размеру batch, числу новых токенов и длине контекста.
   Сначала проверим batch с одинаковыми длинами запросов. До пилота выберем, как
   считать batch с разными длинами и чередовать prefill с decode:
   смешанные шаги мы пока не измеряли.

4. Память будем считать блоками по 16 токенов. KV растёт по мере обработки
   запроса. В нашем прогоне блок занимает 8 MiB, каждой копии доступны 963 блока.
   Перед шагом проверим свободное место с учётом резервов, после завершения
   запроса освободим его блоки. До пилота зададим правило на случай, когда
   памяти не хватает работающим запросам. Проверим, что они не остаются
   в ожидании друг друга.

5. Подключим три политики к одному симулятору. Для переноса сохраним запрос,
   источник, получателя, резерв памяти и этап копирования. Перед копированием
   зарезервируем память получателя. Время передачи посчитаем по объёму KV
   и заданной скорости. Источник продолжает decode во время копирования,
   поэтому учтём новый KV и паузу перед завершением переноса.
   Одним событием сменим копию модели, которая обрабатывает запрос,
   и освободим память источника. Если запрос завершился раньше или перенос
   отменён, освободим резерв получателя.

6. Сначала проверим одну копию модели с заданными вручную временами, затем
   добавим вторую и подключим замеры. После этого добавим политики и переносы.
   Решения политик проверим по [ручным примерам](checkpoints/01.md#расчётная-проверка),
   расчёт метрик — по [учебному журналу](checkpoints/01.md#проверка-расчёта-метрик).
   К КТ2 выполним полный запуск и проведём пилот на синтетике.

### Правила планирования

Во всех трёх вариантах очередь устроена одинаково: сначала `high`,
затем `normal`, внутри класса — по времени поступления, при равенстве — по ID.
Уже начатый шаг не прерываем. Если первому запросу очереди не хватает памяти,
следующие его не обходят, ну а работающие запросы продолжают decode.
Порядок по приоритету и времени поступления берём из
[§4.4.3 статьи](https://www.usenix.org/system/files/osdi24-sun-biao.pdf#page=9).

Для Llumnix считаем $F = (M - V) / \max(B, 1)$: при $B = 0$ делим на 1.
$M$ — вместимость KV-памяти в блоках, $B$ — число выполняющихся запросов.
В $V$ входят занятые и зарезервированные блоки, потребность первого запроса
очереди и общий виртуальный запас $H$. Если есть выполняющиеся запросы `high`,
$H = H_0$, иначе $H = 0$. Запас $H_0$ фиксирован для экземпляра и делится поровну
между его активными `high`: на каждый приходится $H_0 / N_{\mathrm{high}}$
([алгоритм 1, строки 8–10](https://www.usenix.org/system/files/osdi24-sun-biao.pdf#page=9)).
Для основных запусков берём [$H_0 = 675$ блоков](experiment-plan.md#конфигурации-и-план-запусков);
в ручном примере используется отдельное значение 8. Реальную память под этот запас
не резервируем. До завершения переноса запрос входит в $N_{\mathrm{high}}$
только у источника. Если у копии модели нет запросов и резервов, получаем $F = M$.
При равных оценках копий модели выбираем меньший ID.

Переносы проверяем каждые 100 мс модельного времени, начиная с 0.
Источник выбираем с наименьшим $F < 0$, получателя — с наибольшим $F > 2$.
Копии модели с запланированным или идущим переносом пропускаем. За проверку
запускаем не больше одного переноса на пару, если у получателя хватает памяти под резерв.
Запрос выбираем как в ручных примерах: сначала `normal`, затем `high`,
внутри класса — меньшая текущая длина, затем ID. Перед переносом дождёмся
конца текущего шага и ещё раз проверим условия.

Пороги 0 и 2 оставляем из ручных примеров. Делитель при $B = 0$ и период
100 мс выбраны нами конкретно для нашего симулятора.

## Поддерживаемые сценарии

- Смешаем короткие и длинные запросы, изменим интенсивность и сравним очереди
  и загрузку экземпляров.
- Рассмотрим случай, когда первому запросу в очереди не хватает памяти,
  хотя в кластере свободного места достаточно. Проверим, поможет ли перенос.
- Добавим высокоприоритетные запросы к обычной нагрузке и проверим порядок
  их обслуживания и выделяемый для них запас памяти.

## Упрощения

Число экземпляров менять не будем, их характеристики считаем одинаковыми.
Автомасштабирование не рассматриваем. Планировщик не знает будущую длину ответа.

В статье копирование KV идёт параллельно с вычислениями. На финальной стадии
переноса запрос ненадолго останавливается
([§4.2](https://www.usenix.org/system/files/osdi24-sun-biao.pdf#page=6)).
Нулевая пауза в нашем учебном журнале — допущение для проверки метрик.

Время prefill и decode зададим по измеренному профилю выбранной модели.
Для длин и размеров batch между измеренными точками будем оценивать время
по соседним замерам. Такой расчёт проверим на пилоте.
Для миграции отдельно зададим время копирования KV и время остановки запроса.
Выводы будут относиться к этим данным. Чтобы проверить ускорение
высокоприоритетных запросов, время decode в модели должно зависеть от размера batch.

Выводы ограничены выбранными профилями и параметрами симулятора.
Для переноса выводов на реальный сервис потребуются замеры под реальной нагрузкой.
